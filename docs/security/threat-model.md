# Threat model

Mis à jour : 2026-08-27 (audit de sécurité complet post-Phase 14, voir `docs/security/security-assessment-report.md`). Version initiale : Phase 1 (2026-08-24). Ce document est révisé à chaque phase qui touche une frontière de confiance ; ne pas le laisser dériver du code réel est une exigence de ce projet, pas une formalité.

## Périmètre et actifs

Actifs : données d'identité et cliniques, consentements, sessions, politiques de crise, décisions et alertes, contenu de conversation, modèles/datasets d'apprentissage, secrets, audit et canaux de notification.

## Frontières de confiance

Client (patient/clinicien/admin) ↔ API ; API ↔ SQLite (développement) ; API ↔ modèle de risque/émotion (in-process, aucun réseau) ; production ↔ pipeline d'apprentissage ; administration ↔ politiques versionnées. Il n'existe aujourd'hui aucune frontière réseau vers un service IA externe : le répondeur et les modèles sont in-process (voir ADR-004, ADR « répondeur non génératif »). Cela réduit certaines surfaces (pas d'exfiltration vers un tiers) mais n'élimine pas les autres frontières.

| TH-01 | Vol de session ou credential stuffing | Spoofing / API2 | Critique | PBKDF2-HMAC-SHA256 600k itérations (pas Argon2id — écart assumé, voir ADR-003 ; à revoir si une dépendance crypto approuvée devient disponible), MFA obligatoire clinicien **et** admin, rotation de session, rate limiting par (IP, e-mail) | **Vérifié** : `tests/test_security.py::RateLimitingTests`, `tests/test_foundation.py::test_clinician_requires_totp`, `tests/test_security.py::AuthBypassTests` (token trafiqué/révoqué/manquant) |
| TH-02 | BOLA sur profil, conversation, timeline, alertes | Elevation / API1 | Critique | RBAC + relation patient-clinicien active vérifiée côté serveur à chaque appel ; aucune permission implicite côté client | **Vérifié** : tests négatifs dans `test_clinician_dashboard.py`, `test_conversation.py`, `test_learning_pipeline.py`, `test_security.py::PrivilegeEscalationTests` |
| TH-03 | Injection SQL/XSS | Tampering / OWASP | Élevé | Requêtes paramétrées partout (`?` sqlite3), aucune concaténation de valeur utilisateur dans du SQL (2 exceptions documentées et justifiées : `db.py` migration version codée en dur, `clinician.py` clause `IN` à `?` uniquement — voir `# nosec` en ligne) ; échappement HTML côté frontend (`escapeHtml`) partout où du texte utilisateur est inséré en `innerHTML` | **Vérifié** : `test_security.py::InjectionResilienceTests` (payloads SQLi réels contre le login, payload `<script>` stocké et relu tel quel) ; audit manuel de tous les usages `innerHTML` des trois frontends (Phase 10, aucun gap trouvé) |
| TH-04 (ADR-005) | Prompt injection / exfiltration via le modèle conversationnel | IA | Réduit, borné par construction | Depuis ADR-005, un modèle génératif auto-hébergé (`local_llm.py`, Qwen2.5-3B-Instruct, aucune donnée ne quitte le système) répond aux messages GREEN. Le risque classique d'injection de prompt est réel : un patient peut tenter de manipuler le modèle. Son rayon d'impact reste borné par construction, pas seulement par convention : `responder.py::compose_reply` route ORANGE/RED vers des gabarits fixes **avant** tout appel au LLM, qui ne voit donc jamais un message de crise et ne peut structurellement jamais influencer la classification de risque, seulement le texte d'une réponse déjà classée sans danger. Le score PHQ-9 n'est jamais injecté en clair dans le prompt (seule une bande qualitative l'est, voir `personalization.py`), réduisant le risque de fuite verbatim d'une donnée sensible dans une réponse. | **Vérifié structurellement** : `tests/test_generative_responder.py::test_orange_and_red_messages_never_reach_the_generative_engine` (moteur espion, aucun appel enregistré sur un message RED). **Non vérifié** : aucun corpus de tests adversariaux de jailbreak/prompt-injection réel n'a encore été constitué contre le modèle déployé (Section 41 du prompt maître) — à faire avant tout pilote. |
| TH-05 | Fausse décision de crise (le modèle/LLM décide seul) | Safety | Critique | Moteur de règles versionné indépendant + modèle de risque combinés par maximum de score / minimum de confiance (jamais l'inverse) ; le répondeur ne peut jamais produire la réponse ORANGE/RED, seuls des modèles de politique approuvés le peuvent | **Vérifié** : `test_crisis_pipeline.py::CrisisDetectorFailSafeTests`, `test_conversation.py` (RED/ORANGE reçoivent le template fixe, jamais le répondeur) |
| TH-06 | Perte/doublon d'alerte ou de notification | Availability | Élevé (partiel, amélioré) | Idempotence par clé (message → alerte → notification) ; retry synchrone borné (3 tentatives) puis, si toujours en échec, ligne durable `FAILED` reprise en arrière-plan avec backoff exponentiel (1 min → 6 h de plafond) jusqu'à `MAX_TOTAL_ATTEMPTS=10`, exécuté par `scripts/retry_notifications.py` (à planifier via cron/Task Scheduler réel) ; au-delà, la ligne reste `FAILED` avec `next_retry_at=NULL` — une vraie lettre morte interrogeable, jamais silencieusement oubliée | **Vérifié** : `test_crisis_pipeline.py::NotificationRetryTests` (reprise après fenêtre de backoff, mise en lettre morte après `MAX_TOTAL_ATTEMPTS`). **Toujours non résolu (TM-08, ouvert depuis la Phase 5–6, réduit mais pas fermé)** : une panne du processus exactement entre l'insertion de la ligne `PENDING` et la mise à jour finale laisse une ligne orpheline que ni le chemin synchrone ni le worker de reprise actuel ne reprennent (celui-ci n'interroge que `delivery_status='FAILED'`) ; combler ce cas exigerait une réclamation par verrouillage optimiste (`UPDATE ... WHERE attempt_count=<lu>`) sur les deux chemins d'écriture pour éviter un double envoi si le worker et un appel synchrone se chevauchent — jugé hors du périmètre de cette itération, documenté plutôt que masqué |
| TH-07 | Réidentification de données d'apprentissage | Privacy | Critique | Opt-in `LEARNING` révocable, échantillonnage n'incluant que les patients consentants au moment de l'échantillonnage, anonymisation par motifs (e-mail/téléphone), revue humaine obligatoire avant inclusion dans un dataset, file de revue non scopée par relation clinique (réduit le risque qu'un clinicien reconnaisse l'écriture de son propre patient) | **Vérifié** : `test_learning_pipeline.py` (consentement, non-fuite d'identité dans la file de revue). **Non résolu** : anonymisation par motifs insuffisante pour des identifiants non structurés (TM-12) ; révocation n'efface pas rétroactivement un dataset déjà finalisé (limite documentée, Phase 8b) |
| TH-08 | Altération de politique ou de modèle | Tampering | Critique | Politiques de crise et modèles de réponse versionnés en JSON, chargés et validés au démarrage, refusés hors développement sans `approved_by`/`approved_at` ; registre de modèles exigeant deux approbations cliniciennes distinctes (contrainte `UNIQUE` en base, pas seulement applicative) avant déploiement | **Vérifié** : `test_crisis_pipeline.py::PolicyLoadingTests`, `test_learning_pipeline.py` (double approbation, rejet unique bloquant) |
| TH-09 | Journalisation de données sensibles | Information disclosure | Élevé | Le contenu des messages n'est jamais dans les logs applicatifs (seuls `request_id`, actions et résultats le sont) ; les réponses d'erreur ne contiennent jamais de trace Python | **Vérifié** : `test_security.py::SecretLeakageTests` (pas de `password_hash`/`mfa_secret`/`token_hash` dans les réponses, pas de trace dans les 404/400), `scripts/scan_secrets.py` en CI. **Non vérifié** : pas de scan automatisé des logs applicatifs eux-mêmes (seulement du code source) |
| TH-10 | Déni de service | DoS | Élevé (partiel) | `RateLimiter` générique (fenêtre glissante en mémoire) appliqué au login (par IP+e-mail), à l'inscription (par IP, 10/heure) et à l'envoi de message (par patient, 30/minute) ; taille de requête bornée (`MAX_BODY_BYTES`) | **Vérifié** : `test_security.py::RateLimitingTests` (inondation d'inscriptions et de messages, non-blocage des comptes non concernés), `PayloadAndContentTypeAbuseTests` (corps surdimensionné). **Non résolu** : limiteur en mémoire donc non partagé entre plusieurs instances du processus (acceptable en développement, à remplacer par un limiteur distribué avant un déploiement multi-instance) ; pas de limite sur l'échantillonnage d'apprentissage (usage admin uniquement, jugé à moindre risque) ; pas de test de charge/spike réel (Phase 11, non commencée) |
| TH-11 | Traversée de chemin sur le serveur de développement statique | Tampering / API path traversal | Moyen (dev uniquement) | `scripts/dev_server.py::_safe_static_path` résout le chemin et vérifie qu'il reste sous `FRONTEND_ROOT` | **Vérifié** : `test_security.py::PathTraversalTests` (payloads `../`, chemins absolus) |
| TH-12 | Usurpation de session par absence de protection CSRF | Tampering | N/A par construction | L'authentification est un jeton `Bearer` explicite dans l'en-tête `Authorization`, jamais un cookie envoyé automatiquement par le navigateur : il n'y a pas d'« ambient credential » à détourner, donc pas de surface CSRF classique | **Vérifié** : `test_security.py::AuthBypassTests::test_session_endpoint_never_sets_a_cookie` |
| TH-13 | Indisponibilité totale sous un serveur WSGI multi-thread (connexion SQLite partagée entre threads) | Availability | Élevé (corrigé) | Chaque requête ouvre et ferme sa propre connexion SQLite (Phase 11–12) au lieu de partager une connexion unique créée au démarrage, qui aurait levé `sqlite3.ProgrammingError` dans tout thread différent de celui qui l'a créée | **Vérifié** : `test_resilience.py::ConcurrencyTests` (20 threads concurrents, bug reproduit avant correction puis re-testé après) |
| TH-14 (SEC-001) | Race condition (TOCTOU) contournant l'invariant « un rejet clinique bloque définitivement » sur le registre de modèles, la revue d'apprentissage et les transitions d'alerte | Tampering / Safety | Élevé (corrigé) | `UPDATE ... WHERE id=? AND status=<état lu>` avec vérification de `rowcount`, remplaçant un `SELECT` puis `UPDATE` non atomique | **Vérifié** : reproduit de façon déterministe avec deux connexions SQLite séparées avant correction (un rejet réel était silencieusement écrasé par une approbation concurrente) ; `test_security.py::BusinessLogicRaceConditionTests` (3 tests) après correction |
| TH-15 (SEC-002) | Absence de CSP/HSTS/Permissions-Policy (défense en profondeur XSS/clickjacking incomplète) | Tampering / Information Disclosure | Moyen (corrigé) | CSP stricte (`default-src 'none'` sur l'API, `'self'` sur les frontends), HSTS, Permissions-Policy restrictive, sur toutes les réponses sans exception (un seul point d'appel `start_response`, vérifié) | **Vérifié** : `test_security.py::SecurityHeadersTests`, confirmé sans régression dans un navigateur réel (aucune violation CSP, `fetch()` fonctionnel) |
| TH-16 (SEC-003) | Absence de rate limiting sur la soumission PHQ-9 (incohérence avec l'endpoint de message déjà protégé) | Availability | Faible (corrigé) | `RateLimiter` générique, 20/heure/patient | **Vérifié** : `test_security.py::RateLimitingTests::test_phq9_submission_flooding_by_one_patient_is_throttled` |

## Cas d'abus IA prioritaires

- Un acteur cherche à provoquer ou dissimuler une alerte : couvert par les tests d'idempotence et par l'indépendance du moteur de règles.
- Un modèle non validé (émotion) influence une décision de sécurité : structurellement impossible aujourd'hui — `crisis.CrisisDetector` ne référence jamais `backend/app/emotion.py` (voir Phase 8 report).
- Une réponse générée prétend diagnostiquer ou divulgue le contexte d'un autre patient : le prompt système (`local_llm.py::SYSTEM_PROMPT`) l'interdit explicitement et le contexte injecté ne contient jamais les données d'un autre patient (`personalization.py` ne lit que par `patient_id`/`conversation_id` du message courant), mais aucun corpus de tests adversariaux versionné (Section 41 du prompt maître) n'existe encore pour le vérifier empiriquement contre le modèle réellement déployé — à constituer avant tout pilote (voir TH-04, ADR-005).

## Dette de vérification assumée pour la suite

- Pas de scan de logs applicatifs en conditions réelles (seulement du code source via `scan_secrets.py`).
- Rate limiting en mémoire de processus (login, inscription, message, PHQ-9) : non partagé entre plusieurs instances, et le rate limiting par IP suppose l'absence de reverse proxy non configuré (INFO-001, `security-assessment-report.md`).
- Pas de test de charge/résilience réel (chaos engineering, Phases 11–12 du prompt maître, mesure ponctuelle uniquement).
- Le corpus de tests adversariaux IA (jailbreak, injection multilingue) reste à constituer si un LLM réel est un jour intégré.
- Fenêtre de course résiduelle bénigne, sans impact sur l'intégrité des données, documentée en INFO-002 (`security-assessment-report.md`).
